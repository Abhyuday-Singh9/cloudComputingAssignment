The local cloud foundation was bootstrapped using k3d running on top of Docker Desktop. keep_record = (line_number % SHARD_COUNT) == SHARD_INDEX

2. Task 2: Training the Student (Sequence-Level Distillation)

2.1 Distillation Training Setup

The student model selected was EleutherAI/pythia-70m (70 million parameters, GPT-NeoX causal architecture). Fine-tuning was executed completely on CPU-only hardware using PyTorch and Hugging Face Transformers. Configuration parameters were decoupled into training/config.yaml:

  • Random Seed: Fixed at 42 across Python, NumPy, and PyTorch (torch.manual_seed).
  • Learning Rate: $1 \times 10^{-4}$ using AdamW with linear warmup and weight decay of 0.01.
  • Batch Size & Sequence Length: Batch size of 4 with dynamic padding to batch maximum (max sequence cap 64 tokens).
  • Epochs: 3 full epochs across all 1,497 cleaned training records (1,125 training steps total).
  • Prompt Masking: Loss was computed exclusively on the target JSON tokens by masking prompt token labels with -100.

2.2 CPU Optimization & Numerical Stability Breakthrough

An initial training attempt on CPU stalled severely (~90 seconds per step) and resulted in gradient overflow (NaN loss). Investigation revealed that PyTorch default causal loaders loaded weights in torch.float16. Because standard x86 CPUs lack native hardware registers for half-precision floating-point arithmetic, PyTorch fell back to slow software emulation while AdamW squared gradient momentum overflowed the 65,504 FP16 maximum.

By enforcing dtype=torch.float32 across model weights, optimizer buffers, and forward passes, training execution accelerated by 25x (down to 0.82 seconds per step) with 100% numerical stability. Furthermore, replacing static length-128 padding with dynamic batch padding reduced attention matrix FLOPs by $4\times$.

2.5 Theory: Knowledge Distillation Comparative Analysis

1. Sequence-Level Knowledge Distillation (Kim & Rush, 2016)

In Sequence-Level Knowledge Distillation (Seq-KD), the student model is trained on complete, discrete target sequences generated by a high-capacity teacher model. Formally, given an input natural language command $x$, the teacher model parameters $\theta_T$ generate a deterministic output sequence $\hat{y}$ using greedy autoregressive decoding ($\hat{y} = \arg\max_y P(y \mid x; \theta_T)$). The student model $\theta_S$ is then trained by minimizing standard empirical cross-entropy loss against these teacher-generated hard targets:

$$\mathcal{L}_{\text{Seq-KD}}(\theta_S) = - \sum_{t=1}^{|\hat{y}|} \log P(\hat{y}_t \mid \hat{y}_{ In our implementation, the teacher (Phi-3.5) mapped unstructured command strings into structured JSON strings. The student was trained directly on these teacher strings, effectively treating the teacher as an automated, high-speed data labeler.

2. Logit-Based Knowledge Distillation (Hinton et al., 2015; PyTorch Tutorial)

In contrast, Logit-Based (or Token-Level) Knowledge Distillation trains the student to match the full continuous probability distribution across the entire vocabulary at every generation step. Output logits $z_i$ are softened using a temperature hyperparameter $T > 1$:

$$p_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

The total objective function combines ground-truth task cross-entropy with the Kullback-Leibler (KL) divergence between the teacher's softened distribution $p^T$ and the student's softened distribution $p^S$:

$$\mathcal{L}_{\text{Logit-KD}} = (1 - \alpha) \mathcal{L}_{\text{CE}}(y, p^S) + \alpha T^2 \mathcal{D}_{\text{KL}}(p^T \parallel p^S)$$

Logit-based distillation transfers rich "dark knowledge"—the subtle semantic relationships and relative probabilities that the teacher assigns to non-target tokens (e.g., probability mass assigned to synonymous dates or alternate intents).

3. Why Logit-Based Distillation is Infeasible in this Architecture

Logit-based distillation is technically impossible in this project due to two fundamental architectural constraints:

  1. Tokenizer and Vocabulary Incompatibility: Phi-3.5 uses a SentencePiece-derived tokenizer with a vocabulary size of 32,064 tokens, whereas Pythia-70M uses the GPT-NeoX byte-pair encoding (BPE) tokenizer with a vocabulary size of 50,304 tokens. Because token boundaries, subword segmentations, and vocabulary indexes do not correspond ($V_T \neq V_S$), token-level logit tensors cannot be aligned mathematically for KL divergence calculation.
  2. Black-Box Text-Generation API Boundary: The teacher was deployed via Ollama's HTTP REST service. Standard text-generation endpoints emit only the final decoded UTF-8 string. Access to full raw logit matrices ($[B, S, |V|]$) and internal hidden state activations is not exposed over this interface.

4. Critical Limitations of the Implemented Approach

While Sequence-Level KD achieved strong performance, several real-world limitations were observed:

  • Compounded Error Propagation: The student has no access to ground truth; it treats the teacher's outputs as infallible. If Phi-3.5 misclassifies an intent or drops a slot, the student memorizes that error as truth.
  • Severe Parameter Capacity Gap: Pythia-70M ($7 \times 10^7$ parameters) is $54\times$ smaller than Phi-3.5 ($3.8 \times 10^9$ parameters). When confronted with complex linguistic phrasing (e.g., compound calendar dates or nested prepositional phrases), 70M parameters lack sufficient depth to consistently isolate slots without hallucination.
  • Loss of Output Uncertainty (Mode Collapse): Training purely on greedy teacher sequences ($\text{temperature}=0$) forces the student toward unimodal predictions, stripping away alternative valid interpretations.

3. Task 3: The Inference Service in a Container

3.1 Web Service Architecture

The inference service was implemented in service/main.py using FastAPI and Uvicorn. It exposes three primary HTTP endpoints:

  • GET /healthz: Returns HTTP 200 {"status":"alive"} immediately upon process startup.
  • GET /readyz: Returns HTTP 503 {"status":"loading"} while model weights are downloading from S3 and initializing; returns HTTP 200 {"status":"ready"} only after weights are active in memory.
  • POST /parse: Accepts {"text": "..."}, executes greedy decoding, validates against schema.json, and returns HTTP 200 with the 4-key JSON body.

Every response sets two mandatory HTTP tracking headers: X-Model-Version (from MODEL_VERSION) and X-Served-By (the pod hostname injected via the Kubernetes Downward API). Model output is strictly validated: any syntax malformation or missing schema keys triggers HTTP 500 {"error": "invalid_model_output"}. Fault injection is controlled via FAULT_INJECT=1, which intercepts generation and simulates corrupt output to verify failure handling.

3.2 Container Optimization & Minimal Image

The container image was specified in service/Dockerfile based on python:3.11-slim. To prevent bloated image sizes, CPU-only PyTorch wheels were installed directly from the PyTorch repository: 

pip install --no-cache-dir torch --index-url https://download.pytorch.org/whl/cpu

All dependencies in requirements.txt were strictly pinned. In accordance with cloud engineering best practices, model weights and secrets were completely omitted from the image. The resulting image size is 343 MB, substantially below the 2.0 GB requirement.

  1. Zero-Downtime Rolling Update (v1 → v2): While continuous traffic was sent to /parse, environment variables were updated to MODEL_VERSION=v2 and MODEL_URI=s3://models/v2. Because maxUnavailable=0, the old v1 pods continued answering traffic while the new v2 pods downloaded weights.   2. Pod Recovery Under Load: An active pod replica was manually terminated (kubectl delete pod) during inference load. The Kubernetes ReplicaSet detected the deficit and spawned a replacement within 4 seconds. The surviving replica handled 100% of traffic without dropping a single packet.

5.3 Stateless Firewall Theory & Simulator Verification

Verification was performed with tools/nacl_sim.py against network/packets_sample.jsonl, achieving 6 / 6 (100.0%) PASS.

Technical Explanation:
1. Why Stateless NACLs Require Separate Reply Rules: Unlike stateful security groups that maintain an internal connection state table to automatically permit return traffic, stateless network access control lists evaluate every packet in complete isolation. Because the firewall has no memory of outbound requests, separate rules must explicitly allow inbound return packets on ephemeral client ports (1024–65535).
2. Why Rule Ordering Matters for 198.51.100.0/24: NACLs process rules in strictly ascending numerical order with immediate termination on first match. If the abusive block rule (Rule 100) were numbered higher than the public web allow rule (Rule 120), a packet originating from 198.51.100.9 on port 443 would match Rule 120 first and be permitted, defeating the security perimeter.
